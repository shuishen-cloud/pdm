# 设计文档该写什么

每条 feat 对应一份简短设计文档，路径由 `feat.doc` 指定（根目录由
`doc.dir` 控制，默认 `doc`，即 `doc/feat/<slug>.md`）。**先于实现编写**，
它是 feat 阶段的依据。

## 为什么"doc 先行"

阶段流水线 `doc → test → feat → fix → close` 的第一条就是 doc。先把设计
规格定死，写测试和实现才有的放矢；`pdm feat check` 会检查 `empty-doc`。

## 模板

仓库内真实设计文档（如 `doc/feat/stage-commit.md`）遵循以下结构。
照此写：

```markdown
# <一句话标题>（<slug>）

> 先于实现编写。用一两句说明这个设计约束什么。

## 问题

现状哪里不对？用具体例子说明（不要泛泛而谈）。附上**根因**。

## 规范

明确的规则。若是流程/状态，画出流水线：

    doc → test → feat → fix → close

若是数据/接口，给出字段表或类型。

## 接口

```python
def f(x: X) -> Y
    """谁调用、返回什么。"""
```

签名应能直接照着实现（与 `feat.api` 一致）。

## 日志

- 会在什么时机、产出什么日志。不写格式串，写内容/时机。

## 兜底

- 每一条异常路径怎么处理（降级 / 报错 / 跳过）。

## 实现与校验结果（收尾）

**在 close 阶段补写**：实现于哪个 commit，效果如何，实测抓出了什么真实
问题。这一节把设计闭环到事实。
```

## 三栏规格要具体

`feat new` 的 `--api` / `--log` / `--fallback` 必须写成**能直接照着写代码
的程度**，不是占位符：

```bash
# ✅ 好
--api "TokenCache.get(key: str) -> Optional[str]"
--log "缓存未命中时记录 key 与回源耗时"
--fallback "Redis 连接失败降级为直连 DB，记录 warning"

# ❌ 差
--api "提供缓存接口"
--log "打日志"
--fallback "处理异常"
```

## 收尾闭环

close 阶段的文档更新要回答：**这个设计落地后，事实是否印证 / 推翻了它？**
真实设计文档里常见"本次发现的异常"小节，记录执行中暴露的问题——这些
正是下一轮 feat 的输入。

## 存放与跟踪

- 设计正文放 `doc/feat/`（**可跟踪**，随代码分发）。
- `doc.dir` 控制根目录，默认 `doc`；改回 `.pdm/docs` 等不跟踪目录也可。
- doc 阶段的 commit 若无可提交代码文件，可把 README / 索引文件的更新作为
  该阶段的实际内容，避免空提交。
