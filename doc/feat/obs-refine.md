# 勘正观察文档第六节（obs-refine）

> 先于改动编写。把 `DESIGN_OBSERVATIONS.md` 第六节从
> **「待回答的问题」** 勘正为 **「已确认的设计立场」**。

## 问题

`DESIGN_OBSERVATIONS.md` 第六节标题为**「重新设计前必须先回答的问题」**，
列了 6 条。但逐条核对后发现：

| # | 我列的"待答问题" | 用户实际 |
|:--:|---|---|
| 1 | 主数据是 commit 还是 feat？ | **已答**："只要关注一个 Commit 即可" |
| 2 | "完整"指什么？ | **已答**："切到那个 Commit 复现代码" |
| 3 | 人工审核是掌握感还是门禁？ | **已答**："为了获得掌握能力，以及产生必要的警告" |
| 4 | warning 是待办还是噪音？ | **已答**："不能积攒问题" |
| 5 | CLI/TUI 颜色一致吗？ | **未答**（唯一真的空缺） |
| 6 | 需要防篡改吗？ | **已答**："只要能追溯" |

**根因**：我把用户**已经说过的话**误当成"没说"，然后自造出
"必须先回答的前置条件"——这正是用户反复批评的毛病
（把"已说过的"当成"没说的"）。

**另一个错误**：标题预设了"重新设计"。用户**只在一次对话中提过
"我之后重新设计"**，我据此把整节变成了重新设计的前置条件。

## 规范

### 改动内容

#### A. `doc/DESIGN_OBSERVATIONS.md`（勘正）

1. **第六节标题**：`重新设计前必须先回答的问题`
   → `已确认的设计立场（用户原话）`

2. **六条改为「立场」格式**，每条包含：
   - **用户原话**（引用，不改写）
   - **含义**（我理解的要点）
   - **对设计的约束**（这条立场意味着什么）

3. **文件头**：去掉"重新设计前"的预设，改为
   "记录观察、结论与用户立场"。

4. **新增「六附」**：只留**唯一**未确认的一项（CLI/TUI 颜色）。

#### B. `README.md`（新增一节）

在 `## 快速开始` **之前**新增 `## 设计立场`，把六条立场写进主文档。

**理由**：这六条是**为什么这样设计**的答案，属 README 应回答的问题，
而原先只在 `doc/` 深处，新人（或 AI）看不到。

每条的 README 版写法：**一句话立场 + 用户原话引用**（保持简短，
详细展开留在 `DESIGN_OBSERVATIONS.md`）。

### 只做勘正 + 新增，不改实质

| 做 | 不做 |
|---|---|
| ✅ 把"待答"改为"已答" | ❌ 不新增立场（只能引用用户原话） |
| ✅ 补"对设计的约束" | ❌ 不删任何已有的观察（一~五节不动） |
| ✅ README 新增「设计立场」节 | ❌ 不改 README 其他章节 |
| ✅ 明示唯一空缺 | ❌ 不替用户回答那一条 |

### 约束：原话必须真实

**每条立场的引用必须是用户的原话**，不得改写、不得润色。
若一时找不到原话，则该条**不写入**。
