## 一、最本质的三条（设计原则）

### 观察 10：项目推进的关键是「最初设计」与「问题的重新阐释」

**原话要点**：

> "项目能否推进的关键还是最初的设计，以及对于问题的解答，
> 尤其是在对于问题解答过程中对于问题的重新阐释。"

**核实结论**：**成立**。本会话中，AI（我）多次在"把问题转化成任务"，
而用户在"重新阐释问题本身"。

| 用户原问题 | AI 听到的 | AI 做的 | 应做的 |
|---|---|---|---|
| 命令行完善了吗 | 缺哪些命令 | 列缺口清单 | 先问**范围** |
| TUI 有 bug | 怎么修 | 提五条原则 + 估工时 | 先问**哪里不对** |
| api 缺前缀 | 怎么补 | 补校验 + 补数据 | 用户最后说"**没必要对应**" |
| 有无冗余 | 找冗余字段 | 列五类冗余 | 先问**冗余的定义** |

**规律**：AI 解"问的题"，用户在解"该不该这么问"。

**启示**：重新设计时，应先固定**设计意图**，而非数据结构。

### 观察 11：主数据是 commit；质量应一开始最优，不积攒问题

**原话要点**：

> "我最开始的设计就是只要关注一个 Commit 即可，有完整的真实即可
> （如果要检验就切换到那个 Commit 复现代码），而且代码质量不是后来
> 改进的，而是本来就最小优化后的，不能积攒问题。"

**核实结论**：**成立，且推翻 AI 此前的多条建议。**

| AI 曾建议 | 按此原则应判 |
|---|---|
| 反向追溯 `feat find <file>` | **方向错误**——该用 `git log` + 该 commit 的笔记 |
| 补齐 86 条 api 前缀 | **方向错误**——那是"事后补"，违背原则 |
| 把 `feat` 当主数据结构分析 | **前提错误**——`commit` 才是主，`feat` 只是视图 |

**核实证据**：
- `Feat.notes` 字段 39 条全空——真实关联走 `commit hash`
- 现 `check` 有 159 条 warning——**"积攒问题"本身违背此原则**

**待澄清**（必须由用户回答）：
1. 一条 feat 有 5~6 个 commit，"切到那个 commit" 指**哪个**？
2. 阶段流水线（跨 commit）是**核心**还是**辅助**？
3. 159 条 warning：是"待办"还是"噪音"？

### 观察 12：对问题的定义不清楚——要实现什么/怎么实现/为什么

**原话要点**：

> "我对于问题的定义不清楚，要实现什么效果，实现方式是什么，
> 以及这两个问题的为什么，我都没有好好想一想。
> 以及如何设计，最后一无所有。"

**核实结论**：**部分成立——"没写下来"比"没想"更准确。**

用户**已经回答过**这四个问题（散落在对话中）：

| 问题 | 用户的实际回答 |
|---|---|
| 要实现什么效果 | "换回一些掌握感"；让 Agent 被约束；追溯设计与历史 |
| 实现方式 | `pdm` 命令行约束 Agent |
| 为什么（效果） | "AI 加速开发，查看设计/验收/整理文档是反复的事" |
| 为什么（方式） | 要追溯到功能的原始设计，所以 doc 先行 |
| 怎么设计 | `doc → test → script/feat → fix → doc`，Feat 连接多 commit |

**缺的不是"想"，是"落成可检验的判据"**：
- "掌握感"→ 怎么算达成？谁验证？
- 意图散在对话里 → 没变成文档 → 落地时无人发现偏离

**证据（意图丢失的实例）**：
```
初衷：从验收追溯到设计
  ↓ 落地
做了 verify / feat / review 三个独立模块
  ↓ 结果
三者之间没有"追溯"这条路径     ← 初衷丢了，无人发现
```

## 二、结构性问题（已核实）

### 观察 13：接口读不懂——「给什么」不清楚

**原话要点**：

> "我发现项目中的接口设计十分奇怪，有时根本读不懂，
> 有没有什么好阅读的接口设计？"

**核实结论**：**成立**。已产出 `doc/INTERFACE_AUDIT.md`（163 个接口）。

**核心结论**：**"要什么"基本清楚，"给什么"不清楚。**

| 问题类型 | 数量 |
|---|:---:|
| 返回裸容器（`tuple`/`dict`） | 31（占问题 ~60%） |
| 同名跨层（`Feat` vs `FeatStore`） | 5 组 |
| 一词多义（`review` 三义） | 12+ |
| 返回类型不一致 | 3 |

**分级**：A+B 占 79%（良好），问题集中在 **C/D 级 21%**，
恰好是最核心的数据操作。

**D 级（极易调错）6 处**：
- `review_counts() -> tuple`——**已实际造成 bug**（记录见下）
- `review_items() -> List[tuple]`
- `commented_items() -> List[tuple]`（三元组）
- `summarize() -> dict`
- `build_data() -> Dict[str, Any]`（整个 webui 模块）
- `parse_target() -> tuple`

**附加发现（导出时核实）**：`ReviewItem` 与 `StageReview` **未在 `pdev`
顶层导出**（需 `from pdev.feat import ReviewItem`）。

使用者读 `Feat.reviews: dict` 时，**看不出里面装的是 `ReviewItem`**——
因为该类型不在顶层可见，且字段标注只有 `dict`。

已由 `tests/test_design_audit.py::test_review_item_not_exported_at_top_level`
钉住；若将来导出，该测试会失败，届时更新本条。

### 观察 14：测试能否看出接口如何使用？应否更细致分层

**原话要点**：

> "我最初的设想是设计出测试的接口，就要能看出来这些接口如何使用，
> 现在的项目满足了吗（我想应该将测试更加细致地分为一小组）？"

**核实结论**：**不满足**。

**核实数据**：

| 指标 | 实测 | 判定 |
|---|:---:|:---:|
| 测试总量 | 10460 行 / 30 文件 / 798 用例 | 量足 |
| 每测试断言中位数 | 2 | ✅ 颗粒度不粗 |
| 断言 >5 的测试占比 | 3% | ✅ 无"巨型测试" |
| 访问私有属性 | 仅 ~52 处 | ✅ 基本只测公开面 |

**但三处不满足**：

1. **测试名描述"行为"，不描述"调用示例"**
   `test_counts_and_coverage` —— 测什么行为 ✓，怎么调 ✗
2. **主路径藏在断言里**——一个测试混合验证多个接口
3. **没有"接口级"用法示范层**

**文件级问题**：`test_cli.py` **161 个用例 / 1937 行**，
内部已有 20 个分节（**天然拆分线**）：

```
verify              19 用例
feat review         18
pdm feat            13
路径与交互           13
query               12
...
```

**抽象层混杂**：`test_feat.py` 同时测 `Feat`（76 次）与 `FeatStore`（23 次）。

**关键区分**：
- **拆文件** → 解决"找不到在哪"
- **分层目录**（core/cli/ui）→ 解决"这是哪一层"
- **一个对象一个文件** → 解决"在测什么"

**三层都要，但"分层"比"拆细"更重要。**

## 三、数据与结构问题（已核实）

### 观察 8：数据设计是否冗余

### 观察 9：人工审核模块有无冗余/耦合

**核实结论**：**有冗余，也有耦合，且两者同源。**

**冗余（同一逻辑实现两遍）**：

| | `check.py::_check_review` | `review.py::compute_review` |
|---|---|---|
| 覆盖率算法 | `reviewed / items` | `reviewed / items` |
| 告警码 | `review-none`/`review-low` | **`no-review`/`low-review`** |
| 阈值来源 | 函数参数 | `ReviewPolicy.min_coverage` |
| 分档 | 无 | `LEVELS`（excellent/good/...） |

**耦合（三处）**：

1. **`reviews` / `comments` 共享 key 空间**——`doc` 路径一改，
   两个 dict 旧 key 同时变孤儿。
2. **`stage_reviews` 与它们维度不同**——key 是"阶段"而非"可审项"，
   却存放在同一 `Feat` 内。
3. **审查逻辑散落 6 个模块**：check / review / feat / webui / commands / config。

**根因**：
> **因为有冗余（两套算法），所以有耦合（改一处要同步另一处）。**

**根本观察**：
- "掌握感"（人对代码的认知）→ 应归 `reviews` + `comments`
- "流程控制"（阶段门禁）→ 应归 `stage_reviews`
- **两者目的不同，不该共用一套结构**

### 观察（新增）：数据结构不贴现实——把「事件」存成了「状态」

**原话要点**：

> "我的数据结构并没有和现实十分贴切，也许是因为我没有参考
> 一些较为成熟的数据结构的设计。"

**核实结论**：**成立，根因明确。**

**核心失真**：人的判断（审了/评了/核了）**本质是事件**，
但被压成了布尔位和字符串：

| 概念 | 现实（事件） | 现有存储（状态快照） |
|---|---|---|
| 审查 | 谁在何时审了 api:0 | `reviews["api:0"].reviewed = True` |
| 评论 | 谁在何时说了什么 | `comments["api:0"] = "文本"` |
| 阶段审核 | 谁在何时审了 doc | `stage_reviews["doc"] = {...}` |

**证据**：`comments` 有 13 条真实内容，**但无作者、无时间**。

**反例（做对的）**：`Issue.events` 是 `List[Event(at, type, actor, text)]`。
**同一项目里，评论有两种做法。**

**后果**：
- 丢了**谁**、丢了**何时**、丢了**历史**（重审即覆盖）
- 一个语义裂成**三个 dict**

**可参考的成熟范式**：

| 你的概念 | 成熟对应物 | 启示 |
|---|---|---|
| 审查/评论/审核三套 dict | **Event Sourcing** | 状态是事件的投影 |
| `Feat` 15 字段干 7 件事 | **Aggregate** | 一个聚合只保证一组不变式 |
| `status` + `stage` 两套 | **State Machine** | 一个实体一个状态机 |

### 观察（新增）：加一个 kind 要改 6 处

**用户提问**：

> "为什么第一个需要涉及那么多地方？"

**核实结论**：**实测 7 行 / 6 文件**（含全部展示层）。

| 改动点 | 文件 | 行数 |
|---|---|:---:|
| 枚举成员 | `pdev/note.py` | 1 |
| CLI 别名 | `pdev/cli/parser.py` | 1 |
| CLI 颜色 | `pdev/cli/commands.py` | 1 |
| TUI 颜色 | `pdev/tui/panels.py` | 1 |
| TUI 缩写 | `pdev/tui_curses.py` | 1 |
| webui CSS | `pdev/webui.py` | 2 |

**根因三条**：

1. **"颜色"有 4 套表示**：ANSI 码 / Textual 名 / curses 常量 / CSS 十六进制
   → 不是"需要"，是**缺转换层**。
2. **两个 `_KIND_SHORT` 同名不同义**：
   `parser.py` 的是**输入别名**（列表），`tui_curses.py` 的是**显示缩写**（字符串）。
3. **`NoteKind` 只定义了"名字"，没定义"身份"**
   → 颜色/缩写/别名/负债 散成 7 个碎片。

**对照：`stats` 统计只改 5 行 / 2 文件**——因为那是**真新概念**，
而 kind 展示层是**同一件事写 6 遍**。

**判据**：
- **数据层是开放的**（枚举驱动，检索/统计自动生效）✅
- **展示层是散乱的硬编码** ⚠️

**待决策**：
> CLI 与 TUI 的颜色，应"语义一致"还是"各自优化"？
> 现状：`problem` 在 CLI 是红，在 TUI 是亮红（**不一致**）。

## 六、已确认的设计立场（用户原话）

> **本节记录用户已经明确表达过的立场**，不是待办。
> 此前误列为"待回答的问题"，实为已在对话中回答——此处勘正。

### 立场 1：主数据是 commit，feat 是视图

> "我最开始的设计就是只要关注一个 Commit 即可，有完整的真实即可
> （如果要检验就切换到那个 Commit 复现代码）"

**含义**：每个 commit 应当**自洽完整**；要复现/检验，切到那个 commit 即可。
`feat` 是**组织多个 commit 的视图**，不是必须依赖的第二份真相。

**对设计的约束**：
- 笔记、验证、设计信息都应能**从单个 commit 定位**
- `feat` 只负责"把相关 commit 串起来"，不应成为信息的**唯一**存放处

### 立场 2：质量是设计出来的，不是事后补的

> "代码质量不是后来改进的，而是本来就最小优化后的，不能积攒问题"

**含义**：不接受"先欠着、以后修"。

**对设计的约束**：
- warning 不应长期堆积（当前 168 条本身就违反此原则）
- `check` 的规则要么可行动、要么不报
- 历史豁免（如 `FIELDS_SINCE`）与此原则有张力

### 立场 3：人工审核有两个目的

> "后期在其中穿插人工验收与审核也是为了获得对于代码的掌握能力，
> 以及产生必要的警告"

**含义**：审核**同时**服务两个目的——**掌握能力**与**产生警告**。

**对设计的约束**：
- "掌握感"（人对代码的认知）与"门禁"（流程阻断）是两件事
- 现有 `reviews` / `stage_reviews` 共用一套结构，是**目的混淆**的结果

### 立场 4：doc 流程是为了追溯

> "借助那些之前的 doc 一系列流程，可以很快追溯到一个功能的设计与历史
> （如果是从头就开始就进行管理的话，并且有 Feat 抽象连接多个 Commit）"

**含义**：追溯是 doc 流程的**目的**；`Feat` 的作用是连接多 commit。

**对设计的约束**：
- 追溯**双向**才有意义（设计→测试；测试→设计）
- 当前只有单向（设计→接口→测试），反向无入口

### 立场 5：初衷是减少反复

> "我设计这个项目的初衷是因为 AI 加速开发流程，查看设计以及验收
> 还有整理文档是一件颇为反复的事情"

**含义**：消除"查设计/验收/整理文档"的重复劳动。

**对设计的约束**：
- 每个信息只应维护**一处**（当前"单一真相"问题的根源）
- 入口应**唯一**（`Ledger` 门面的动机，但目前无人使用）

### 立场 6：主要使用形式是命令行约束 Agent

> 来约束 Agent，实现对于 Agent 十分强大的约束"

**含义**：**CLI 是主要接口**，用于约束 Agent。

**对设计的约束**：
- Python 层 API 的"好不好看"**次要**于 CLI 的约束力

- 约束的关键在**门禁**（提交前拒绝），而非事后审计
